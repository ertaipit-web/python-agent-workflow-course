# RAG Lab

Компактная лаборатория, где retrieval показан как инженерный компонент агентной системы, а не как отдельный курс. Агент получает вопрос, решает, что ему не хватает фактов, вызывает разрешённый retrieval tool, читает только нужные фрагменты и отвечает на основе найденного контекста.

```text
User
 → Agent
 → Retrieval tool (search_documents)
 → Vector store
 → Retrieved context (read_chunk)
 → Agent
 → Answer with citations
```

Агент **не получает весь корпус**. Инструмент поиска возвращает ссылки, оценки и короткие сниппеты; полный текст читается только для выбранных фрагментов. Это тот же приём Just-in-Time Context, который разобран в неделе 3 курса, только в виде кода.

## Требования и установка

- Python 3.11 или новее

Из каталога `labs/rag-lab`:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev]"
.\.venv\Scripts\python.exe -m pytest
```

В корневом окружении курса:

```powershell
.\.venv\Scripts\python.exe -m pip install -e ".\labs\rag-lab[dev]"
.\.venv\Scripts\python.exe -m pytest .\labs\rag-lab\tests
.\.venv\Scripts\python.exe -m rag_lab --corpus .\labs\rag-lab\corpus --cases .\labs\rag-lab\questions.json
```

Один вопрос вместо всего набора:

```powershell
.\.venv\Scripts\python.exe -m rag_lab --corpus .\labs\rag-lab\corpus --cases .\labs\rag-lab\questions.json --case outside-the-corpus
```

## Что реализовано

| Шаг | Модуль | Что важно |
|---|---|---|
| Ingestion и chunking | `src/rag_lab/chunking.py` | Разбиение Markdown по секциям и скользящему окну; у каждого chunk есть документ, секция и идентификатор. |
| Embeddings | `src/rag_lab/embedding.py` | Детерминированный локальный embedder без внешних пакетов и API. |
| Vector store и поиск | `src/rag_lab/store.py` | In-memory индекс, cosine similarity, порог отсечения, top-k. |
| Retrieval tool | `src/rag_lab/tools.py` | Два узких инструмента с явной схемой аргументов и проверкой до исполнения. |
| Агент и ответ | `src/rag_lab/agent.py` | Цикл поиск → чтение → ответ, отказ при отсутствии опоры в контексте, trace. |
| Оценка | `src/rag_lab/evaluation.py` | Тот же набор метрик, что в неделе 7: релевантность retrieval, groundedness, доля неподкреплённых ответов. |

## Границы офлайн-реализации

Встроенный embedder — это хеширование слов в фиксированное число измерений с L2-нормализацией. Он не понимает смысл и не знает синонимов: вопрос «права доступа» не найдёт фрагмент про least privilege. Это сделано намеренно, чтобы было видно главное:

- качество retrieval ограничено embedder-ом, поэтому его измеряют, а не считают само собой разумеющимся;
- хеш-коллизии дают ложные совпадения с ненулевой оценкой, поэтому проверка «есть ли в контексте опора для ответа» обязана быть отдельным шагом, а не следствием порога поиска;
- детерминированный extractive-ответчик не может выдумать факт, которого нет в загруженном фрагменте.

Заменить embedder и ответчик на свои реализации нужно за интерфейсами `HashingEmbedder` и `Answerer`, то есть тем же приёмом, что `ModelClient` в неделе 5. Тогда `run_question`, инструменты и оценка останутся прежними.

## Негативный сценарий

В `questions.json` два случая с `"supported": false`:

- `outside-the-corpus` — вопрос вообще не про этот корпус; поиск не находит ничего релевантного;
- `no-evidence-in-corpus` — поиск возвращает похожие фрагменты, но ни один не отвечает на вопрос.

В обоих случаях агент возвращает `insufficient_context` и не выдумывает ответ. Если заменить extractive-ответчик на модель, этот статус перестаёт быть гарантированным: оценка `unsupported_answer_rate` покажет, появились ли неподкреплённые ответы.

## Формат `questions.json`

```json
{
  "case_id": "handoff-fields",
  "question": "What must every handoff artifact contain?",
  "supported": true,
  "expected_sources": ["handoff-contract.md"]
}
```

`case_id` уникален, `expected_sources` обязателен для поддерживаемых случаев и пуст для неподдерживаемых. Нарушение любого правила останавливает загрузку набора, а не превращается в тихо пропущенный кейс. Добавляйте свои вопросы и документы: оценка пересчитается при следующем запуске.

## Практика

1. Прогоните набор и запишите три метрики из отчёта.
2. Уменьшите `--top-k` до 1 и посмотрите, какие поддерживаемые вопросы перестали находить свой документ.
3. Поднимите порог `min_score` в `RetrievalTools` так, чтобы поиск почти ничего не возвращал, и объясните, что произошло с метриками.
4. Сравните объём переданного контекста с объёмом корпуса: это и есть проверка принципа «retrieve only the context needed for the current task».
5. Замените `ExtractiveAnswerer` на свой, используя provider из недели 4, и измерьте, как изменились groundedness и `unsupported_answer_rate`.
6. Добавьте документ, который отвечает на один из неподдерживаемых вопросов, и переведите его в поддерживаемый — так проверяется, что набор, а не код, определяет ожидания.

## Границы и безопасность

Лаборатория работает локально, не требует API-ключей и не обращается в сеть. Внешние зависимости нет: используются только стандартная библиотека и pytest. Инструменты работают с локальным индексом, ничего не пишут в корпус и не запускают команды. Не помещайте в `corpus/` секреты, `.env` и персональные данные: содержимое фрагментов попадает в отчёт и в trace.
