# AGENTS.md

## 1. Язык общения

Все сообщения в окне чата, отчёты, пояснения, планы, summaries и результаты работы выводи **только на русском языке**.

Исключения:

* имена файлов;
* имена классов, функций, переменных;
* команды CLI;
* названия библиотек, API, технологий и стандартных терминов;
* фрагменты кода;
* commit messages, если для них используется английский формат.

Не переключайся на английский язык без необходимости.

---

## 2. Git: никогда не commit и не push без явной инициативы пользователя

**Никогда самостоятельно не выполняй:**

```bash
git commit
git push
git reset --hard
git rebase
git clean -fd
```

без явной команды пользователя.

По умолчанию:

* изменяй рабочие файлы;
* проверяй результат;
* показывай `git diff --stat`;
* показывай, какие файлы изменены;
* сообщай о результате тестов/build.

Но оставляй изменения **не закоммиченными и не запушенными**, пока пользователь явно не попросит сделать commit/push.

Если пользователь написал только «проверь», «исправь», «сделай задачу» — этого недостаточно для commit/push.

## 5. Не расширяй curriculum без необходимости

Не добавляй новые большие темы только потому, что они существуют на рынке.

Перед добавлением нового раздела оцени:

1. решает ли он реальную проблему текущего курса;
2. связан ли он с существующей архитектурой;
3. есть ли практический результат;
4. нельзя ли решить задачу меньшим изменением;
5. не дублирует ли он уже существующий материал.

Предпочтение:

```text
reuse existing material
>
rewrite existing material
>
small extension
>
new section
>
new module
```

Если изменение заметно увеличивает объём курса или меняет его позиционирование, сначала сообщи об этом пользователю.

---

## 6. Не бойся увеличивать объём ради понимания

Ограничение курса по объёму не является абсолютным.

Можно добавлять:

* worked examples;
* небольшие эксперименты;
* failure cases;
* короткие пояснения;
* схемы;
* bridge между концепциями;
* практические мини-задания.

Если дополнительный материал существенно улучшает понимание — его добавление оправдано.

Но не добавляй:

* filler;
* длинные исторические справки;
* повторные объяснения;
* маркетинговый текст;
* материал ради формального увеличения часов.

Главный критерий:

> минимальный достаточный объём для хорошего понимания, а не минимальный возможный объём.

## 7. Объясняй сложные концепции через проблему

Для новых концепций предпочтительна последовательность:

```text
Проблема
↓
Пример
↓
Что пошло не так
↓
Идея решения
↓
Термин
↓
Реализация
↓
Практика
```

Не предполагай, что студент уже знает Agent Engineering terminology.

При первом существенном появлении специализированного термина дай короткое объяснение.

Например:

> **Baseline (базовая версия)** — простая рабочая реализация, с которой мы сравниваем более сложное решение.

После первого объяснения можно использовать термин без повторной расшифровки.

## 8. Не пиши курс как RFC

Избегай избыточно плотного инженерного языка.

Если инструкция выглядит как:

## 10. Mermaid

В проекте используется native Mermaid через Zensical.

Не заменяй Mermaid другой системой без причины.

После изменения Mermaid или `zensical.toml` обязательно проверяй:

```bash
zensical build --strict
```

Проверяй также:

* light mode;
* dark mode;
* mobile;
* отсутствие overflow;

Не считай успешный build достаточным, если диаграмма фактически не отображается.

## 14. Учебные примеры должны быть технически корректными

Код в учебном материале должен соответствовать тексту.

Особенно проверяй:

* exception flow;
* retry logic;
* schemas;
* tool call lifecycle;
* permissions;
* state transitions;
* mock providers;
* API examples.

Не оставляй пример, который выглядит красиво, но фактически не работает.

Если пример намеренно демонстрирует плохой подход, явно пометь его:

> **Anti-pattern**

или аналогичным callout.

---

## 15. Не смешивай разные уровни абстракции

Не вводи одновременно много новых компонентов без объяснения связей.

Используй:

> проблема → потребность → abstraction

Например:

```text
Нужно хранить данные между шагами
→ State

Нужно отделить provider
→ ModelClient

Нужно управлять переходами
→ Workflow
```

---

## 16. Архитектурные решения должны быть проверяемыми

Не утверждай, что архитектура лучше просто потому, что она сложнее.

По возможности сравнивай:

* качество;
* стоимость;
* latency;
* количество model calls;
* error rate;
* human intervention;
* business outcome.

Multi-agent не является целью сам по себе.

Если deterministic workflow лучше — так и должно быть.

Если агент вообще не нужен — это хороший инженерный результат.

---

## 17. Security и side effects

Для инструментов и интеграций сохраняй принципы:

* least privilege;
* explicit permissions;
* scopes;
* allowlist;
* validation;
* human approval для опасных операций;
* tracing;
* predictable errors;
* minimal required access.

Не ослабляй существующую security model ради простоты примера.

---

## 18. Не добавляй зависимости ради одной маленькой задачи

Перед добавлением библиотеки проверь:

1. можно ли решить задачу существующими средствами;
2. есть ли уже подходящая dependency;
3. действительно ли новая библиотека нужна студенту;
4. усложнит ли она установку labs.

Для учебного курса предпочтение отдаётся минимальному и понятному стеку.

---

## 19. Работай небольшими, проверяемыми изменениями

Для каждой задачи:

1. изучить существующий материал;
2. определить минимальный набор файлов;
3. внести изменения;
4. проверить build/tests;
5. проверить визуальный результат, если меняется сайт;
6. показать краткий отчёт.

Не делай unrelated refactoring.

Не исправляй случайные вещи, которые не относятся к текущей задаче, если они не создают непосредственную проблему для результата.

---

## 20. При неоднозначности сначала используй контекст репозитория

Сначала:

* прочитай существующий код;

Но если решение действительно меняет scope, curriculum или архитектуру проекта — остановись и сообщи об этом до внесения такого изменения.

## 24. Главный принцип работы

Этот репозиторий — не просто набор Markdown-файлов.

Это учебный продукт.

При каждом изменении стремись улучшить хотя бы одно из:

* понимание;
* практическую применимость;
* инженерную корректность;
* навигацию;
* визуальное восприятие;
* воспроизводимость.

Но не жертвуй одним из них ради декоративности.

### Целевая формула

> **Same engineering depth → clearer explanation → better practice → lower cognitive load.**
