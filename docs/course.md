# Продвинутый практикум: мультиагентная разработка на Python

**Уровень:** для разработчика, уже работающего с Python и AI coding tools.  
**Ритм:** 8 недель, ориентир 3–5 часов в неделю; можно пройти интенсивом.  
**Основной результат:** проверяемый Python-оркестратор для безопасной мультиагентной работы над задачами кодовой базы.  
**Инструменты:** Kilo Code, Ollama, Python, pytest и Git; LangGraph — как второй слой оркестрации. Платный API не обязателен.

Программа рассчитана на опыт, похожий на ваш: вы уже используете Kodacode и Kilo AI, пишете на Python, а установка пакетов не является препятствием. Поэтому здесь не будет вводных занятий по промптам или установке Python. Вместо этого разбираются архитектура агентов, handoff-контракты, маршрутизация, ограничение действий, локальные модели, интеграция с VS Code/Kilo, тестирование и наблюдаемость.

## Что в материалах сайтов Zerocoder полезно для этого курса

На страницах практикумов выделяются два полезных формата: много практики с быстрым работающим результатом и демонстрация мультиагентной команды, которая делит создание сайта на роли. Это хорошая мотивация для маленького сквозного проекта, но не готовая инженерная спецификация. В этом курсе подход переносится на Python-репозиторий и дополняется тем, что необходимо разработчику: критериями качества, проверяемыми handoff-ами, ограничением инструментов, git-границами, тестами и оценкой локальной модели.

- [Первый практикум по вайбкодингу](https://zerocoder.ru/pervyy-praktikum-po-vaybkodingu) описывает 80% практики/демонстрации и 20% теории, создание сайта русскоязычными запросами и быстрые MVP.
- [Практикум Claude Code](https://zerocoder.ru/claude-code) заявляет демонстрацию мультиагентной команды, создания вариантов HTML-сайтов и обсуждение применимости инструмента. Мы используем идею разделения труда, но не предполагаем, что инструмент или модель сама по себе даёт надёжную автономию.

Рекламные обещания скорости/экономии не являются гарантией результата. Главный объект практикума — не «попросить несколько ИИ написать код», а построить процесс, который можно проверять и безопасно остановить.

# Исходные условия: компьютер и локальная модель

## Что можно ожидать от 14 ГБ RAM и Ryzen с 8 потоками

По числу потоков и объёму оперативной памяти нельзя точно предсказать скорость: неизвестны конкретный CPU, видеокарта и её VRAM, тип памяти, доступная память после запуска VS Code и ОС, а также длина контекста. Ниже предполагается **14 ГБ системной RAM и преимущественно CPU-инференс**. Если у вас есть дискретная GPU, сообщите модель и VRAM — выбор может измениться.

Для такого компьютера локальная модель годится для экспериментов с короткими агентными задачами, структурированными ответами и отдельными изменениями. Это **не** эквивалент Claude/Kilo cloud и не комфортный запуск рекомендованных Kilo больших coding-agent моделей.

### Модели для первого сравнения

1. **Начать с `qwen3:8b`** — кандидат на общий локальный чат и вызовы инструментов. Официальная страница семейства Qwen3 описывает поддержку агентных сценариев. Начните с контекста 8K и одиночного запроса, прежде чем подключать агента, который читает репозиторий.
2. **Сравнить с `qwen2.5-coder:7b`** — отдельный кандидат для Python-генерации, объяснения и правок кода. Не считать автоматически надёжным Kilo tool-calling агентом: проверить вызов инструментов конкретной версией модели.

Эти команды указаны на страницах моделей Ollama. Точный тег и доступность могут меняться; проверьте актуальные страницы перед скачиванием: [Qwen3](https://ollama.com/library/qwen3) и [Qwen2.5-Coder](https://ollama.com/library/qwen2.5-coder).

```powershell
ollama pull qwen3:8b
ollama run qwen3:8b
```

Завершить интерактивную сессию Ollama: `/bye`. Затем, если есть место и желание сравнить именно кодовую модель:

```powershell
ollama pull qwen2.5-coder:7b
ollama run qwen2.5-coder:7b
```

**Не начинайте с `qwen3-coder:30b`, `devstral:24b` или моделей с похожими требованиями.** Документация Kilo называет их текущими рекомендациями для локального coding agent и указывает ориентир GPU VRAM 24 ГБ+ либо Mac с 32 ГБ unified memory. Это не соответствует исходной конфигурации 14 ГБ системной памяти. Не путайте оперативную память компьютера с VRAM видеокарты.

У `qwen3:8b` и `qwen2.5-coder:7b` квантование, размер контекста и реальный расход памяти влияют на помещаемость модели. Оставьте память ОС, VS Code и другим приложениям; если Windows начинает активно использовать файл подкачки, модель тормозит или не загружается, уменьшите модель/контекст или завершите другие задачи. Не обещаем конкретную скорость без измерения на вашем Ryzen.

### Контекст для вашего объёма RAM

Для первого Kilo-теста попробуйте **8 192 токена (8K)**; если устойчиво хватает памяти — **16 384 (16K)**. Это практический компромисс, не «идеальный контекст» и не рекомендация Kilo для больших репозиториев. Kilo указывает, что для обсуждаемых им крупных моделей желательно не менее 32K, однако 32K на 14 ГБ системной RAM может привести к нехватке ресурсов. Длинный контекст требует дополнительной памяти, а не только места для весов модели.

Для агента со сканированием репозитория лучше сузить контекст за счёт явного списка файлов и короткого запроса, чем сразу увеличивать его до 32K. Не запускайте несколько локальных генераций параллельно на CPU, пока не измерили, что компьютер справляется.

# Практикум 0. Установка Ollama и диагностика на Windows

Этот раздел — отдельная техническая лабораторная. Он разбирает распространённую путаницу: модель может отвечать в приложении Ollama, но не быть добавленной в нужный чат VS Code или не быть выбрана как провайдер Kilo.

## 0.1 Установка и проверка службы

1. Установите Ollama с [официального сайта](https://ollama.com/download).
2. Запустите приложение Ollama. В Windows оно обычно поднимает локальную службу в фоне.
3. Откройте PowerShell и проверьте CLI:

   ```powershell
   ollama --version
   ollama list
   ```

4. Если модели ещё нет, скачайте одну из рекомендованных выше. После скачивания повторите `ollama list`.
5. Проверьте, что локальный HTTP API отвечает:

   ```powershell
   Invoke-RestMethod http://127.0.0.1:11434/api/tags
   ```

   В JSON должен быть список моделей. Можно также проверить OpenAI-совместимый маршрут:

   ```powershell
   Invoke-RestMethod http://127.0.0.1:11434/v1/models
   ```

6. Загрузите модель отдельным smoke test:

   ```powershell
   ollama run qwen3:8b
   ```

   Введите короткий запрос, дождитесь ответа и выйдите командой `/bye`.

Установка приложения, наличие скачанных весов и доступность API — три разные вещи. Запросы в `/api/tags` и `/v1/models` проверяют, что VS Code/Kilo в принципе может увидеть службу и модель.

### Полезные команды Ollama

```powershell
ollama list                 # скачанные модели
ollama ps                   # модели, сейчас загруженные в память
ollama show qwen3:8b        # сведения о модели
ollama pull qwen3:8b        # скачать/обновить модель
ollama run qwen3:8b         # интерактивный чат в терминале
```

Внутри интерактивного чата `ollama run` команда `/show info` показывает сведения о загруженной модели, `/bye` завершает диалог. `pull` только загружает веса; `run` запускает диалог. Отдельное `ollama serve` обычно не нужно, если приложение уже запустило сервер.

Если хотите закрепить настройки контекста за отдельным тегом модели, создайте текстовый файл с именем `Modelfile` в удобной папке:

```text
FROM qwen3:8b
PARAMETER num_ctx 8192
PARAMETER temperature 0.2
```

Затем в этой папке:

```powershell
ollama create qwen3-8b-ctx8k -f .\Modelfile
ollama run qwen3-8b-ctx8k
```

Новый тег использует исходные веса `qwen3:8b`, но задаёт меньший контекст по умолчанию. Для Kilo всё равно задайте согласованный лимит контекста в настройках провайдера. Если используете 16K, создайте отдельный тег с `PARAMETER num_ctx 16384` и сначала проверьте расход памяти.

## 0.2 Когда нужен `ollama serve`

На Windows приложение Ollama часто уже запустило сервер. **Не запускайте второй сервер вслепую.** Если `http://127.0.0.1:11434/api/tags` отвечает, сервер уже работает; отдельная команда `ollama serve` обычно сообщит, что порт занят. Запускайте её вручную только если приложение/служба не запущена и вы осознанно хотите видеть серверные логи в отдельном окне PowerShell. Это окно нужно оставить открытым.

Ollama по умолчанию привязывается к localhost. Для VS Code и Kilo на том же компьютере не нужно открывать API в локальную сеть или интернет и не следует менять bind на `0.0.0.0`.

## 0.3 Две разные интеграции в VS Code

### Вариант A: модель в собственном чате VS Code от Ollama

Это путь, если хотите видеть ответы в **VS Code Chat**, а не только в приложении Ollama:

1. Убедитесь, что Ollama запущена, `ollama list` показывает модель, а `/api/tags` отвечает.
2. В VS Code откройте Extensions и установите официальное расширение **Ollama** из Marketplace: [Ollama extension](https://marketplace.visualstudio.com/items?itemName=Ollama.ollama).
3. Откройте панель Chat в VS Code.
4. В меню выбора модели снизу чата выберите модель из группы **Ollama**.
5. Если список пуст: откройте Command Palette (`Ctrl+Shift+P`) → `Ollama: Refresh Models`; затем `Ollama: Diagnose Models`; проверьте канал вывода **Ollama**.

По актуальной инструкции Ollama это расширение требует VS Code 1.127 или новее и обнаруживает локальные модели по `http://127.0.0.1:11434`. Это интеграция с VS Code Chat; она не делает модель автоматически активной в Kilo.

### Вариант B: модель в чате и режимах Kilo Code

Если хотите, чтобы отвечал именно **Kilo**, нужно выбрать Ollama как провайдера внутри Kilo:

1. Убедитесь, что endpoint работает:

   ```powershell
   Invoke-RestMethod http://127.0.0.1:11434/api/tags
   ```

2. В панели Kilo откройте выбор модели/настройки провайдера (иконка настройки/gear).
3. В списке **API Provider** выберите **Ollama** — не **Ollama Cloud**. Cloud — удалённый сервис; он не подключается к `localhost`.
4. В поле локального base URL укажите `http://127.0.0.1:11434` (если поле показывается; это стандартный локальный адрес).
5. Выберите или введите точное имя модели, как показывает `ollama list`, например `qwen3:8b`.
6. Установите контекст сначала `8192`; если тест показывает, что память позволяет — попробуйте `16384`.
7. Увеличьте **API Request Timeout** в настройках Kilo, если локальный CPU-инференс не успевает в стандартные 10 минут. Начните, например, с 20 минут, но не маскируйте зависшую генерацию бесконечным таймаутом.
8. Сохраните настройки и выберите эту модель для текущего режима/сессии Kilo.
9. Проверьте в коротком чате обычный ответ, затем отдельным минимальным заданием проверьте tool calling. Не сразу давайте Kilo право менять большой репозиторий.

У Kilo есть отдельная инструкция [Using Ollama With Kilo Code](https://kilo.ai/docs/ai-providers/ollama). Если модель не появилась в picker, документация Kilo позволяет добавить custom model в конфигурацию. Пример ниже задаёт модель и лимиты; вставлять его следует в конфиг Kilo, который открыт из настроек, а не в `settings.json` VS Code:

```json
{
  "model": "ollama/qwen3:8b",
  "provider": {
    "ollama": {
      "models": {
        "qwen3:8b": {
          "name": "Qwen3 8B (local)",
          "tool_call": true,
          "limit": {
            "context": 8192,
            "output": 2048
          }
        }
      }
    }
  }
}
```

`tool_call: true` сообщает Kilo, что модель следует использовать как поддерживающую вызов инструментов; это **не** гарантирует, что конкретный тег хорошо вызывает инструменты. Удалите/не добавляйте этот флаг, если модель фактически не справляется с вызовами. Проверьте схему настроек Kilo и формат custom model в [Custom Models](https://kilo.ai/docs/code-with-ai/agents/custom-models) на установленной версии: конфигурация продукта может меняться.

## 0.4 Отдельно: подключение через OpenAI-compatible API

Провайдер **Ollama** в Kilo предпочтительнее, если он доступен: меньше ручной настройки. Если другой инструмент умеет только OpenAI-compatible API, Ollama документирует локальный endpoint:

```text
Base URL: http://127.0.0.1:11434/v1
API key: ollama
Model: точное имя из ollama list, например qwen3:8b
```

Значение `ollama` здесь — совместимый заполнитель: локальный сервер игнорирует API key. Не путайте endpoint `/v1` с интерфейсом провайдера Kilo Ollama, которому обычно указывается сам базовый адрес.

Короткая проверка из Python (по документации Ollama OpenAI compatibility):

```python
from openai import OpenAI

client = OpenAI(
    base_url="http://127.0.0.1:11434/v1",
    api_key="ollama",
)

response = client.chat.completions.create(
    model="qwen3:8b",
    messages=[{"role": "user", "content": "Ответь одной строкой: локальный API работает"}],
)
print(response.choices[0].message.content)
```

Пакет: `python -m pip install openai`. Перед использованием в Kilo сначала добейтесь успешного ответа этим тестом или проверкой `/v1/models`.

## 0.5 Диагностика по симптому

| Симптом | Проверка / действие |
|---|---|
| `ollama` не распознана в PowerShell | Перезапустите терминал после установки; проверьте установку приложения и его PATH. |
| `/api/tags` не отвечает | Запустите приложение Ollama; проверьте, не остановлена ли служба. Не открывайте порт наружу. |
| API отвечает, но моделей нет | `ollama list`; при отсутствии модели — `ollama pull <точный-тег>`. |
| Модель отвечает в приложении Ollama, но отсутствует в VS Code Chat | Установите Ollama VS Code extension, проверьте версию VS Code, выполните Refresh Models и Diagnose Models. |
| VS Code Chat видит модель, Kilo — нет | Это независимые интеграции. В Kilo отдельно выберите API Provider = Ollama и локальную модель. |
| Kilo не соединяется | Проверьте, что выбран локальный **Ollama**, не Ollama Cloud; проверьте адрес localhost, затем проверьте `/api/tags`. |
| Kilo отвечает текстом, но не выполняет tools | Проверить режим Kilo, tool-call поддержку/настройку модели и минимальный tool test; не считать обычный ответ доказательством поддержки tools. |
| Запрос зависает/ошибка таймаута | Сократите контекст и промпт, отключите MCP на проверку, увеличьте API Request Timeout умеренно, измерьте время. |
| Компьютер начинает свопить | Закройте лишние приложения, снизьте контекст, оставьте одну модель/один запрос, попробуйте меньший размер. |

# Архитектура курса

## Учебный репозиторий

Не используйте вначале production-репозиторий. Создайте отдельный небольшой Python-проект с тестами и Git-репозиторием. Добавьте несколько намеренно ограниченных задач: объяснить модуль, написать тест для функции, выполнить маленький рефакторинг. Не подмешивайте секреты и личные данные.

### Основной capstone

**Команда агентов для безопасного решения Python issue**:

```text
issue + ограничения
       ↓
triage/planner
       ↓ (человек утверждает план и допустимый scope)
repo analyst ─── test analyst       ← независимые чтения можно распараллелить
       └────────────┬───────────────┘
                    ↓
                implementer
                    ↓
              test runner
                    ↓
                reviewer
             ↙ замечания  ↘ чисто
        implementer       финальный отчет
                    ↓
              человек принимает diff
```

Не поручайте агенту самостоятельно мержить или публиковать изменения. Исполнение shell-команд — ограниченная возможность с явными разрешениями и аудитом. Для первого прототипа агент только предлагает команды, а разработчик запускает их сам.

## Роли

1. **Triage/Planner:** переводит issue в критерии приёмки, гипотезы и список затронутых областей.
2. **Repo Analyst:** читает заданные файлы и находит релевантные определения/зависимости; возвращает ссылки `path:line`, не пишет код.
3. **Test Analyst:** сопоставляет критерии с существующими тестами и предлагает тест-кейсы; не меняет production-код.
4. **Implementer:** меняет минимальный scope в отдельной ветке после утверждения плана.
5. **Test Runner:** запускает только разрешённые команды тестирования и возвращает stdout/stderr, exit code и точную команду.
6. **Reviewer:** проверяет diff относительно issue, API-совместимость и недостающие тесты; замечание должно ссылаться на строки diff.
7. **Orchestrator:** маршрутизирует этапы, валидирует контракты, сохраняет артефакты и останавливает цикл при неоднозначности.

Это логические роли, а не обязательные семь разных моделей или запущенных процессов. На локальном Ryzen большинство шагов лучше выполнять одной моделью последовательно. Параллелить стоит чтение двух действительно независимых областей, а не несколько длительных генераций на слабом CPU.

# Неделя 1. Переносим coding-agent практику в проверяемый процесс

## Цель

Взять знакомый вам сценарий из Kilo/Kodacode и определить, где мультиагентность реально добавляет качество, а где достаточно одного агента.

## Материал

Разделяйте три свойства, которые часто смешиваются:

- **роль** — какая задача поручена модели;
- **агентный runtime** — как модель получает инструменты, историю и разрешения;
- **оркестрация** — кто и по каким правилам вызывает следующую роль.

Несколько ролевых промптов в одном чате — это ещё не независимые агенты. Реальная система должна определить отдельные контексты, границы доступа, выходные данные, условия перехода и поведение при отказе.

Для каждой знакомой задачи кодинга опишите:

```text

Условие остановки:
```

## Практика

1. решение одним обычным coding agent;

Используйте одинаковый issue и одинаковые критерии приёмки. Не сравнивайте только стиль ответа: учитывайте правильность diff, пройденные тесты, пропущенные требования и количество ручных вмешательств.

- выбранная задача для capstone;
- список измеряемых критериев;
- аргумент, почему выбранная задача выигрывает от multi-agent подхода.

# Неделя 2. Архитектуры: последовательность, manager-worker, DAG

## Материал

### Patterns

- **Sequential pipeline:** шаги передаются по очереди. Хорош для issue с чётким порядком.
- **Manager-worker:** координатор делегирует независимые исследования, затем синтезирует результаты.
- **Map-reduce:** одинаковую операцию выполняют над набором независимых элементов, потом результаты сводятся.
- **Router:** классификатор выбирает один путь по типу задачи.
- **Generator–critic:** автор и проверяющий работают по разным критериям; цикл ограничен по числу повторов.
- **Supervisor:** оркестратор выбирает следующий шаг по состоянию. Требует особенно чётких ограничений, иначе сложно отлаживать.

Не делайте агента ради названия паттерна. У каждого дополнительного вызова есть стоимость по времени, контексту, вычислениям и вероятности расхождения.

### Таблица выбора topology

| Свойство задачи | Предпочтительный паттерн |
|---|---|
| Проверка должна идти после написания | Pipeline |
| Два специалиста читают независимые модули | Manager-worker / параллельный DAG |
| Маршрутизация по типу issue: bug/test/docs | Router |
| Нужно свести вывод по нескольким независимым файлам | Map-reduce |
| Автономный агент меняет код по обратной связи | Generator–critic с лимитом итераций |

### Handoff-контракт для coding агента

```json
{
  "status": "complete | needs_input | blocked",
  "summary": "Краткое резюме результата",
  "evidence": [
    {"path": "src/module.py", "lines": "20-37", "claim": "причина связана с ..."}
  ],
  "assumptions": [],
  "open_questions": [],
  "next_action": "что должен сделать следующий узел",
  "files_changed": [],
  "commands_run": []
}
```

На практике схему нужно валидировать, например Pydantic-моделью. Не позволять свободному тексту незаметно пройти как структурированный успех. Для `blocked` и `needs_input` переход должен быть явным, не success-shaped fallback.

## Практика

Нарисуйте граф capstone. Укажите:

- какие узлы read-only;
- какие узлы имеют право создать diff;
- на каких ребрах требуется решение человека;
- какие ошибки завершают запуск;
- максимальное число попыток;
- какие входы двух задач действительно независимы.

# Неделя 3. Контекст-инжиниринг и специализация ролей

## Материал

Coding agent часто ошибается не из-за «слабого промпта», а потому что не получил нужный контракт, файлы, тесты или ограничение scope. Подавайте контекст слоями:

1. цель и критерии приёмки;
2. repo-specific правила и формат;
3. только релевантные файлы/фрагменты;
4. краткие результаты предыдущих ролей с evidence;
5. разрешения текущего этапа.

Длинная история чата — не замена управляемому состоянию. Передавайте между ролями подтверждённые выводы, ссылки на исходники и открытые вопросы, а не целый неструктурированный transcript.

## Шаблон роли planner

```text
Ты — issue planner. Не редактируй файлы и не придумывай устройство репозитория.

Issue:
{issue}

Правила проекта:
{project_rules}

Верни JSON по схеме:
{
  "acceptance_criteria": ["..."],
  "unknowns": ["..."],
  "files_to_inspect": ["..."],
  "files_maybe_to_change": ["..."],
  "test_plan": ["..."],
  "risk_level": "low|medium|high",
  "needs_human_approval": true
}

Если критерий неоднозначен или изменение затрагивает данные/безопасность/API,
остановись со статусом needs_input.
```

## Шаблон роли repo analyst

```text
Ты — read-only аналитик репозитория. Файлы не меняй и команды не запускай.

Исследуй только эти пути:
{allowed_paths}

Issue и критерии:
{issue_and_acceptance}

Верни:
- найденные определения с path:line и коротким подтверждающим фрагментом;
- связи с вызывающим кодом и тестами;
- что осталось неизвестным;
- какие пути нужно исследовать дальше.

Не делай вывод о содержимом файла, которого не видел. Не предлагай широкую
перепись архитектуры, если минимальное изменение решает issue.
```

## Шаблон роли reviewer

```text
Ты — независимый reviewer diff. Код не меняй.

Issue/критерии:
{issue}

Diff:
{diff}

Результаты тестов:
{test_results}

На каждое замечание верни:
severity, file:line, нарушение, доказательство, сценарий отказа, уверенность.
Не сообщай о проблемах, которых нельзя подтвердить diff или тестом.
Отдельно напиши критерии, которые не удалось проверить.
```

## Практика

На одном issue измените отдельно:

- размер переданного контекста;
- подробность роли;
- формат результата;
- наличие path:line evidence.

Запишите, что действительно изменило успех, а что только увеличило токены. Сохраните промпты версионированными файлами, а не только в истории чата.

# Неделя 4. Ollama как локальный model server и Kilo как клиент

## Цель

Убедиться, что модель видна не только в Ollama app, но и именно в том интерфейсе, где вы ожидаете ответы: VS Code Chat или Kilo.

## Лабораторная

Выполните технические шаги раздела «Практикум 0» по порядку. Зафиксируйте:

```text
Видно ли в VS Code Chat:
Видно ли в Kilo:
Работает ли обычный ответ:

Время первого и повторного ответа:
```

## Конфигурация контекста в Kilo

В настройках provider Kilo выставьте Context Window Size (`num_ctx`) в **8192** для первого прогона. Лимит в модели и лимит, заявленный клиенту, должны быть согласованы. Если настраиваете custom model, укажите реалистичные `limit.context` и `limit.output`; не заявляйте Kilo 32K, если сервер и RAM этого не выдерживают. `output` можно ограничить 2048–4096 токенами, чтобы агент не генерировал чрезмерно длинные ответы.

Если модель отвечает, но Kilo продолжает присылать контекст и получает отказ, проверьте ограничения токенов и настройки модели. Если она загружается слишком долго, начните с короткой сессии, не подключайте все MCP и не держите рядом несколько моделей.

## Практика: раздельный smoke test

Проверьте по одному:

1. Ollama CLI — модель отвечает.
2. Ollama API — `/api/tags` и `/v1/models` отвечают.
3. VS Code Ollama extension — модель доступна в Chat.
4. Kilo — выбран provider Ollama, модель и небольшой контекст.
5. Kilo обычный чат — модель выдаёт корректный ответ.
6. Kilo read-only задача — находит существующий файл и ссылается на него.
7. Kilo tool call — только в disposable учебном репозитории и без опасных разрешений.

При провале фиксируйте слой, где перестало работать. Не переустанавливайте всё подряд, пока не выяснили: CLI, служба, endpoint, расширение или provider Kilo.

# Неделя 5. Python-оркестратор поверх локального API

## Материал

Перед подключением LangGraph реализуйте малый orchestrator на Python. Для первого варианта достаточно официального OpenAI-compatible endpoint Ollama и `openai` SDK. Это помогает увидеть реальные сообщения и ошибки API, не скрытые framework-ом. Ollama также имеет собственный Python SDK; выберите один клиент и не смешивайте API в первом прототипе.

Вызов локального completion проверяется так:

```python
from openai import OpenAI

client = OpenAI(
    base_url="http://127.0.0.1:11434/v1",
    api_key="ollama",
)

result = client.chat.completions.create(
    model="qwen3:8b",
    messages=[
        {"role": "system", "content": "Верни только JSON с ключом status."},
        {"role": "user", "content": "Начни проверочный запуск."},
    ],
)
print(result.choices[0].message.content)
```

Этот пример проверяет транспорт и генерацию, а не надёжность JSON. В рабочем оркестраторе обязательно валидируйте ответ Pydantic/dataclass/jsonschema, обрабатывайте пустое сообщение, ошибку сервера, таймаут и превышение длины.

### Компоненты

- `ModelClient`: локальный HTTP клиент, timeout, retry только для временных ошибок.
- `RoleRunner`: собирает system/user messages и вызывает конкретную роль.
- `State`: Pydantic-модель состояния задачи и статусов узлов.
- `Workflow`: явный порядок шагов и переходы.
- `ArtifactStore`: сохраняет prompts, outputs, diff и тестовые результаты без секретов.
- `HumanGate`: возвращает `needs_approval`; не автоматизирует подтверждение кликом.
- `RunPolicy`: разрешённые пути и команды, лимит циклов, ограничение времени.

### Состояние задачи

```text
run_id
issue
acceptance_criteria[]
allowed_paths[]
plan
human_plan_approved
repo_evidence[]
test_plan[]
proposed_patch
commands_requested[]
commands_approved[]
test_results[]
review_findings[]
iteration_count
status: planning|needs_approval|implementing|testing|blocked|done
```

Секреты, `.env`, токены и содержимое credentials не должны попадать в промпты, артефакты логов или commit. Используйте `.gitignore`, redaction и отдельный учебный репозиторий.

## Практика

Соберите первую цепочку без автоматического shell:

```text
issue → planner → schema validation → человек утверждает план
     → repo analyst → test analyst → один отчёт
```

На выходе программа печатает артефакт и предлагает следующий шаг; она не меняет код. Добавьте тесты на JSON invalid, timeout и `needs_input`.

# Неделя 6. Tool calling, разрешения и Kilo modes

## Материал

Наличие агента в IDE означает потенциальный доступ к чтению/редактированию файлов и запуску команд. Разделяйте:

- модель предлагает вызов инструмента;
- клиент интерпретирует вызов;
- политика разрешает или отклоняет его;
- пользователь подтверждает побочный эффект.

Не считать эти уровни взаимозаменяемыми. Хороший тест — дать модели инструкции вызвать только безопасный read-only инструмент и убедиться, что некорректный аргумент отклоняется до исполнения.

### Минимальная политика для курса

- читать только открытый учебный репозиторий и разрешённые подкаталоги;
- изменять только feature branch/worktree;
- не запускать shell-строки, составленные моделью, без просмотра человеком;
- разрешённый список тестовых команд хранить в конфиге;
- не выполнять `rm`, массовые миграции, сетевые публикации, деплой и git push автоматически;
- перед изменением файла показывать diff;
- остановиться, если изменение выходит за scope утверждённого плана.

Kilo имеет свои режимы и разрешения, а Kodacode — свои. Настраивайте каждый инструмент отдельно. Локальный model endpoint не ограничивает права IDE-агента: права определяются клиентом и его tools.

## Практика

На disposable-репозитории попросите Kilo:

1. только объяснить функцию;
2. предложить тест без его запуска;
3. прочитать небольшой список разрешённых файлов;
4. предложить минимальный diff;
5. дождаться подтверждения перед применением и тестированием.

Проверьте, что модель не подменила условие задачи и не просит бессмысленные широкие разрешения.

# Неделя 7. Оценка качества, трассировка и регрессии

## Материал

Оценивать надо весь pipeline, а не только итоговый ответ. Подготовьте «golden set» из 10–20 небольших issue с ожидаемым поведением. Храните входы, версии промптов/моделей, структурированные выходы, решения человека и тестовые результаты. Не используйте приватные репозитории как публичные eval-данные.

### Метрики

- issue resolution rate — выполнены ли критерии приёмки;
- regression rate — внесены ли новые ошибки;
- test pass rate — прошли ли определённые до изменения тесты;
- reviewer precision — доля полезных замечаний без ложных срабатываний;
- scope adherence — менялись ли только разрешённые пути;
- tool-call success — валидны ли аргументы и вызван ли правильный инструмент;
- human intervention — число вмешательств и минуты проверки;
- latency / tokens / memory — длительность и нагрузка локального прогона.

Не сводите эти метрики в один «магический» score. LLM-as-judge можно использовать как дополнительный сигнал, но не как замену тестам и человеческому code review.

### Набор тестов на отказ

1. Issue неполный — planner возвращает `needs_input`.
2. В репозитории нет упомянутого символа — analyst не выдумывает его.
3. Тест падает до изменения — сохраняются baseline и точный exit code.
4. Модель предлагает чужой файл — policy отклоняет scope violation.
5. Ответ не соответствует JSON schema — следующий узел не запускается.
6. Reviewer повторно находит замечание — цикл прекращается по лимиту.
7. Инструмент не отвечает — ошибка видна пользователю, процесс не выдаёт success.
8. Агент предлагает опасную команду — выполнение блокируется до человека.

## Практика

Прогоните golden set на двух конфигурациях: `qwen3:8b` с 8K контекстом и привычный вам Kilo provider/режим, если доступен. Для локального сравнения учтите, что ваш текущий основной провайдер может быть значительно сильнее; цель — измерить локальные границы, а не доказать равенство моделей.

# Неделя 8. Capstone и разбор архитектуры

## Реализуйте

Python-оркестратор с topology:

```text
planner
  └─ человеческое утверждение плана
       ├─ repo analyst (read-only)
       └─ test analyst (read-only)
             ↓
       implementer (предлагает diff)
             ↓
       human approval before writes
             ↓
       test runner (только allowlisted команды)
             ↓
       reviewer (read-only, с доказательствами)
             ↓
       final summary + открытый PR/diff для человека, без автопубликации
```

## Что должно быть в проекте

- схемы состояния и каждого handoff-а;
- роли с разными правами и промптами;
- конфигурация выбранной модели и контекста;
- поддержка ошибок API, невалидной схемы, timeout и отмены;
- лимит повторов;
- allowlist путей и тестовых команд;
- журналирование версий промптов, модели, latency, результатов узлов и решений человека;
- тесты на happy path и перечисленные негативные сценарии;
- документация, как запустить локально и как переключить модель/provider.

## Критерии завершения

- минимум 10 сценариев golden set;
- по каждому запуску можно объяснить, почему сработал именно этот агент/переход;
- недостающий факт или неопределённость приводят к `needs_input`, не к выдуманному ответу;
- ни один shell command/file write не исполняется без соответствующей политики и подтверждения;
- цикл ревью конечен;
- отчёт показывает качество, ограничения модели и долю ручной работы;
- запуск воспроизводим в чистом учебном окружении.

## Архитектурный review

В финале ответьте:

1. Почему здесь нужны роли, а не один агент?
2. Какой узел самый дорогой/медленный?
3. Какие два узла можно безопасно параллелить и на каких данных?
4. Какие общие ошибки все роли могут унаследовать?
5. Где существует риск утечки данных или чрезмерных разрешений?
6. Что заменится при переходе с локальной модели на облачную, а что должно остаться неизменным?
7. Что не следует автоматизировать даже при улучшении модели?
