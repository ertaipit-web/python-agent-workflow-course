# Продвинутый практикум: мультиагентная разработка на Python

**Уровень:** для разработчика, уже работающего с Python и AI coding tools.  
**Ритм:** 8 недель, ориентир 3–5 часов в неделю на обязательное ядро. Дополнительные эксперименты увеличивают нагрузку; интенсивный темп — на усмотрение слушателя.
**Основной результат:** минимальный проверяемый Python-workflow для безопасного решения задачи в кодовой базе.
**Инструменты:** Python, pytest и Git — ядро; для живого запуска Python-workflow нужен model API через небольшой адаптер. Подойдёт локальный Ollama или уже доступный API-provider; одна только IDE-подписка Kilo/Kodacode не обязательно даёт API-доступ для собственного Python-клиента. Kilo — для baseline и ручной проверки в IDE, LangGraph — необязательное сравнение после работающего workflow. Тесты workflow можно писать с mock provider-ом, платный API не обязателен.

## Центральная модель курса: агент — это система вокруг LLM

```text
LLM ≠ Agent

Agent system:
LLM
→ context / state
→ tools
→ runtime / orchestration
→ policy / permissions
→ evaluation / observability
```

LLM генерирует ответы и предлагает действия, но агентное поведение возникает только внутри системы, которая подаёт контекст и состояние, вызывает инструменты, управляет переходами, применяет права и проверяет результат. Надёжность определяется всей этой системой, а не одной моделью или удачным промптом.

Изучайте прежде всего устойчивые концепции: **state, context, tools, structured outputs, orchestration, handoffs, policies, permissions, human-in-the-loop, failure handling, evaluation и tracing/observability**. OpenAI/Anthropic и другие providers, LangGraph, Ollama, IDE agents, MCP и другие протоколы — конкретные реализации или интеграции этих концепций. **Tools change. Architecture remains.** Владение framework само по себе не означает владения agent engineering.

## Целевая аудитория и входной уровень

Курс для Python-разработчика, который уже использует AI coding tools и умеет самостоятельно запускать проектные команды, читать diff и проверять изменения. Нужны практические навыки Python, Git, pytest или аналогичного тестового runner-а, понимание HTTP/JSON и базовая работа с терминалом.

Курс **не для начинающих программистов** и не учит Python с нуля, основам установки пакетов или первым промптам. Опыт с Ollama, LangGraph, MCP и агентными framework-ами не требуется: они вводятся в контексте инженерных задач. Если пакет или инструмент установить не проблема, но автономные агенты пока не строились — это подходящий уровень.

Курс строится вокруг небольшого Python-репозитория: handoff-контракты, ограничение действий, eval, tracing и безопасная работа с изменениями. В каждой неделе сначала выполняется обязательное ядро; расширения можно пропускать без потери основного результата.

### Что является обязательным ядром

- Один baseline coding agent и один минимальный multi-agent workflow сравниваются на одних и тех же задачах.
- Capstone реализует только необходимую цепочку: `planner → read-only analyst → proposed patch → human approval → tests → reviewer/report`.
- Для моделей используется один provider, выбранный слушателем. Переключение моделей, локальная интеграция, LangGraph и MCP — расширения, а не входные условия.
- Политики и проверки сначала реализуются простым Python-кодом; framework подключается только при конкретной необходимости.

В занятиях встречаются метки **Обязательное ядро** и **Расширение**. Выполнение расширений не требуется для зачёта основного курса.

## Что в материалах сайтов Zerocoder полезно для этого курса

На страницах практикумов выделяются два полезных формата: много практики с быстрым работающим результатом и демонстрация мультиагентной команды, которая делит создание сайта на роли. Это хорошая мотивация для маленького сквозного проекта, но не готовая инженерная спецификация. В этом курсе подход переносится на Python-репозиторий и дополняется тем, что необходимо разработчику: критериями качества, проверяемыми handoff-ами, ограничением инструментов, git-границами, тестами и оценкой локальной модели.

- [Первый практикум по вайбкодингу](https://zerocoder.ru/pervyy-praktikum-po-vaybkodingu) описывает 80% практики/демонстрации и 20% теории, создание сайта русскоязычными запросами и быстрые MVP.

Рекламные обещания скорости/экономии не являются гарантией результата. Главный объект практикума — не «попросить несколько ИИ написать код», а построить процесс, который можно проверять и безопасно остановить.

# Архитектура курса

## Учебный репозиторий

Не используйте вначале production-репозиторий. Для воспроизводимой практики можно взять подготовленный [учебный репозиторий курса](lab-repository.md) или создать disposable Python-проект по следующей спецификации:

```text
src/
tests/
docs/
issues/
```

Подготовьте 5 основных issue с критериями приёмки и известным ожидаемым поведением:

1. небольшой bug с воспроизводящим тестом;
2. задача «добавить тест», не меняя production-код;
3. документационная правка с ограниченным scope;
4. неоднозначный запрос, для которого правильный результат — `needs_input`;
5. небольшое изменение с регрессионным edge case.

**Расширение:** добавьте red-team issue с prompt injection в тексте задачи/фикстуре и доведите набор до 10 кейсов.

Для сравнения прогоняйте одни и те же issue в baseline и workflow. Не подмешивайте секреты и личные данные. Если готового starter repository нет, этот список — минимальная спецификация для его подготовки, а не отдельная задача по разработке полноценного учебного продукта.

### Основной capstone

**Проверяемый workflow для безопасного решения Python issue**:

```text
issue + ограничения
       ↓
   planner
      ↓
          человек утверждает scope
      ↓
       read-only analyst (код + тесты)
      ↓
          implementer предлагает diff
      ↓
         человек подтверждает запись
      ↓
          allowlisted tests + review
      ↓
       diff и отчет принимает человек
```

Разделять analyst на repo analyst и test analyst нужно только если эксперимент показывает пользу. Не поручайте агенту самостоятельно мержить или публиковать изменения. Исполнение shell-команд — ограниченная возможность с явными разрешениями и аудитом. Для первого прототипа агент предлагает команды, а разработчик запускает их сам.

## Роли

Роли ниже — каталог возможных обязанностей, а не требование реализовать семь отдельных агентов. В обязательном ядре можно объединить чтение репозитория и анализ тестов в одну read-only роль.

1. **Triage/Planner:** переводит issue в критерии приёмки, неизвестные и допустимый scope.
2. **Read-only Analyst:** находит релевантный код и тесты, возвращает ссылки `path:line`; не пишет код.
3. **Implementer:** предлагает минимальный diff внутри утверждённого scope.
4. **Test Runner:** запускает разрешённые проверки и возвращает команду, stdout/stderr и exit code.
5. **Reviewer:** проверяет diff по критериям и evidence; может быть отдельной ролью или отдельным этапом проверки человеком.
6. **Orchestrator:** валидирует handoff-контракты, состояние, policy и условия перехода.

**Расширение:** выделить Test Analyst и независимого Reviewer в отдельные model calls, только если измеримо улучшается результат.

Это логические роли, а не обязательные отдельные модели или процессы. Параллелить стоит только действительно независимые чтения, если это оправдано выбранным provider и средой.

# Неделя 1. Переносим coding-agent практику в проверяемый процесс

## Цель

Взять знакомый вам сценарий из Kilo/Kodacode и определить, где мультиагентность реально добавляет качество, а где достаточно одного агента.

## Материал

Разделяйте три свойства, которые часто смешиваются:

- **роль** — какая задача поручена модели;
- **агентный runtime** — как модель получает инструменты, историю и разрешения;
- **оркестрация** — кто и по каким правилам вызывает следующую роль.

Несколько ролевых промптов в одном чате — это ещё не независимые агенты. Реальная система должна определить отдельные контексты, границы доступа, выходные данные, условия перехода и поведение при отказе.

Для каждой знакомой задачи кодинга опишите:

```text
Задача/issue:
Критерии приёмки:
Какие файлы можно читать:
Какие файлы можно менять:
Разрешённые команды:
Запрещённые действия:
Кто принимает план:
Кто проверяет diff:
Условие остановки:
```

## Практика

Возьмите 3–5 issue из подготовленного учебного набора. Для обязательного ядра:

1. зафиксируйте результат обычного одиночного coding agent на этих issue;
2. реализуйте минимальный процесс «planner → read-only analyst → implementer → проверка»;
3. повторите на том же issue и с теми же критериями, сравнив итоговый diff, тесты и время ручной проверки.

Не сравнивайте только стиль ответа: учитывайте выполнение критериев, регрессии, нарушения scope и количество ручных вмешательств. Не нужно строить три разные архитектуры.

**Расширение:** сравнить с «planner → implementer → reviewer» или распараллелить двух независимых read-only аналитиков.

## Результат недели

- baseline на 3–5 подготовленных задачах;
- выбранная задача для capstone;
- список измеряемых критериев;
- аргумент, почему выбранная задача выигрывает от multi-agent подхода.

**Обязательное ядро:** baseline и один кандидатный workflow.
**Расширение:** сравнение нескольких топологий на всём наборе.

**Что переносится за пределы coding agents?** Сравнение с baseline — общий экспериментальный метод для проверки, оправдано ли усложнение любого workflow.

# Неделя 2. Архитектуры: последовательность, manager-worker, DAG

## Материал

### Patterns (обзор; реализуется только одна топология)

- **Sequential pipeline:** шаги передаются по очереди. Хорош для issue с чётким порядком.
- **Manager-worker:** координатор делегирует независимые исследования, затем синтезирует результаты.
- **Map-reduce:** одинаковую операцию выполняют над набором независимых элементов, потом результаты сводятся.
- **Router:** классификатор выбирает один путь по типу задачи.
- **Generator–critic:** автор и проверяющий работают по разным критериям; цикл ограничен по числу повторов.
- **Supervisor:** оркестратор выбирает следующий шаг по состоянию. Требует особенно чётких ограничений, иначе сложно отлаживать.

Не делайте агента ради названия паттерна. У каждого дополнительного вызова есть стоимость по времени, контексту, вычислениям и вероятности расхождения. Перед добавлением роли ответьте: **почему недостаточно одного агента; какую отдельную ответственность получает новая роль; какова цена дополнительного handoff; каким eval на том же baseline будет измерено улучшение?** Если улучшение не обнаруживается в качестве, регрессиях, scope adherence или ручной проверке, оставьте более простую архитектуру.

### Таблица выбора topology

| Свойство задачи | Предпочтительный паттерн |
|---|---|
| Проверка должна идти после написания | Pipeline |
| Два специалиста читают независимые модули | Manager-worker / параллельный DAG |
| Маршрутизация по типу issue: bug/test/docs | Router |
| Нужно свести вывод по нескольким независимым файлам | Map-reduce |
| Автономный агент меняет код по обратной связи | Generator–critic с лимитом итераций |

### Handoff-контракт для coding агента

```json
{
  "status": "complete | needs_input | blocked",
  "summary": "Краткое резюме результата",
  "evidence": [
    {"path": "src/module.py", "lines": "20-37", "claim": "причина связана с ..."}
  ],
  "assumptions": [],
  "open_questions": [],
  "next_action": "что должен сделать следующий узел",
  "files_changed": [],
  "commands_run": []
}
```

На практике схему нужно валидировать, например Pydantic-моделью. Не позволять свободному тексту незаметно пройти как структурированный успех. Для `blocked` и `needs_input` переход должен быть явным, не success-shaped fallback.

## Практика

**Обязательное ядро:** нарисуйте один граф capstone и отметьте:

- какие узлы read-only;
- какие узлы имеют право создать diff;
- на каких ребрах требуется решение человека;
- какие ошибки завершают запуск;
- максимальное число попыток;
- где система должна остановиться при неизвестном.

**Расширение:** реализуйте второй паттерн и обоснуйте его измеримую пользу.

**Что переносится за пределы coding agents?** Выбор topology и явный handoff применимы к любому workflow, где этапы обмениваются ограниченными данными и имеют проверяемые условия перехода.

# Неделя 3. Контекст-инжиниринг и специализация ролей

## Материал

**Context Engineering** — проектирование того, какая информация доступна модели на конкретном шаге. Контекст — не только prompt: это system/developer instructions, conversation/history, task state, определения tools и их результаты, retrieved information, внешние данные, релевантные артефакты, constraints и permissions. Runtime/policy, а не текстовая инструкция, обеспечивает исполнение permissions.

Не помещайте весь доступный контекст в каждый model call. Цель — дать модели нужный контекст в нужный момент: достаточный для текущего решения, но без нерелевантной истории, файлов и результатов инструментов.

Вместо передачи всего репозитория используйте Just-in-Time Context:

```text
agent определяет, чего не хватает
→ вызывает разрешённый read/search tool
→ получает только релевантный фрагмент с источником
→ обновляет task state / evidence
→ продолжает workflow
```

Например, repo analyst сначала получает issue, критерии и разрешённые пути, затем находит определения и тесты и передаёт implementer-у только подтверждённые `path:line`, нужные фрагменты и открытые вопросы. Так state связывает найденный контекст с задачей, не превращаясь в копию всей истории.

Coding agent часто ошибается не из-за «слабого промпта», а потому что не получил нужный контракт, файлы, тесты или ограничение scope. Подавайте контекст слоями:

1. цель и критерии приёмки;
2. repo-specific правила и формат;
3. только релевантные файлы/фрагменты;
4. краткие результаты предыдущих ролей с evidence;
5. разрешения текущего этапа.

Длинная история чата — не замена управляемому состоянию. Передавайте между ролями подтверждённые выводы, ссылки на исходники и открытые вопросы, а не целый неструктурированный transcript.

## Шаблон роли planner

```text
Ты — issue planner. Не редактируй файлы и не придумывай устройство репозитория.

Issue:
{issue}

Правила проекта:
{project_rules}

Верни JSON по схеме:
{
  "acceptance_criteria": ["..."],
  "unknowns": ["..."],
  "files_to_inspect": ["..."],
  "files_maybe_to_change": ["..."],
  "test_plan": ["..."],
  "risk_level": "low|medium|high",
  "needs_human_approval": true
}

Если критерий неоднозначен или изменение затрагивает данные/безопасность/API,
остановись со статусом needs_input.
```

## Шаблон роли repo analyst

```text
Ты — read-only аналитик репозитория. Файлы не меняй и команды не запускай.

Исследуй только эти пути:
{allowed_paths}

Issue и критерии:
{issue_and_acceptance}

Верни:
- найденные определения с path:line и коротким подтверждающим фрагментом;
- связи с вызывающим кодом и тестами;
- что осталось неизвестным;
- какие пути нужно исследовать дальше.

Не делай вывод о содержимом файла, которого не видел. Не предлагай широкую
перепись архитектуры, если минимальное изменение решает issue.
```

## Шаблон роли reviewer

```text
Ты — независимый reviewer diff. Код не меняй.

Issue/критерии:
{issue}

Diff:
{diff}

Результаты тестов:
{test_results}

На каждое замечание верни:
severity, file:line, нарушение, доказательство, сценарий отказа, уверенность.
Не сообщай о проблемах, которых нельзя подтвердить diff или тестом.
Отдельно напиши критерии, которые не удалось проверить.
```

## Практика

**Обязательное ядро:** на одном issue проверьте, помогает ли передача `path:line` evidence и типизированного результата по сравнению со свободным текстом.

**Расширение:** меняйте по одному параметру — размер контекста, подробность роли, формат результата — и сравните качество с ростом токенов. Сохраняйте промпты версионированными файлами.

**Короткое упражнение (5 минут):** возьмите issue из Repo Triage и составьте два входа analyst-у: полный текст README/истории и минимальный контекст из issue, критериев, разрешённых путей и найденных фрагментов. Запишите, какую информацию можно получить по требованию через read-only tool, и сравните релевантность evidence и объём переданного контекста.

**Расширение:** retrieval как инструмент. Пошаговый пример — ingestion, chunking, embeddings, vector search, retrieval tool и отказ отвечать без источника — собран в [RAG-лабораторной](rag-lab.md). Основной идеей остаётся та же: `retrieve only the context needed for the current task`, а retrieved-фрагменты считаются недоверенными данными с источником, как и любой вывод инструмента.

**Что переносится за пределы coding agents?** Контекст с источниками, границами и открытыми вопросами — общий принцип передачи задачи между любыми компонентами или исполнителями.

# Неделя 4. Подключение выбранного model provider

## Цель

Убедиться, что выбранный provider отвечает в интерфейсе или API, который будет использоваться в Python-workflow. Kilo — привычный инструмент для ручного baseline, но не runtime capstone.

## Обязательное ядро

Выберите один доступный provider и выполните минимальный smoke test. Запишите:

```text
Provider и модель:
Способ вызова (SDK/API/IDE):
Успешен ли короткий запрос:
Есть ли structured output или tool calling:
Latency первого и повторного запроса:
Какие ограничения/стоимость/приватность нужно учитывать:
```

Если нет доступного model API, тесты и реализацию workflow можно продолжить с mock `ModelClient`; для демонстрации живого агентного прогона настройте Ollama или API-provider. Неудача с локальной моделью не блокирует остальные занятия.

## Расширение: локальная модель в Ollama, VS Code и Kilo

Если хотите работать локально или сравнить IDE-интеграции, пройдите [техническую лабораторную по Ollama/VS Code/Kilo](local-models.md). Она справочная и не является prerequisite следующих недель.

**Что переносится за пределы coding agents?** Provider adapter отделяет логику приложения от конкретного поставщика модели и упрощает замену реализации без переписывания workflow.

# Неделя 5. Provider-agnostic Python-оркестратор

## Материал

Реализуйте небольшой orchestrator на Python без framework-а. Вынесите различия provider-а в `ModelClient`: его интерфейс принимает сообщения и ограничения, возвращает typed result или явную ошибку. Для вызова выберите уже доступный SDK/API; центральная логика workflow не должна знать о конкретном endpoint. Локальный пример Ollama приведён в [технической лабораторной](local-models.md).

Независимо от SDK валидируйте ответ Pydantic/dataclass/jsonschema; обрабатывайте пустой результат, ошибку provider-а, timeout и превышение длины. Unit-тесты workflow должны использовать fake/mock `ModelClient`, чтобы не требовать локальную модель или платный API.

### Компоненты

Границы компонентов для проектирования; не обязательно строить полноценную инфраструктуру для каждого:

- **Обязательное ядро:** `ModelClient` (с timeout и ограниченным retry), `State`, `Workflow`, `HumanGate`, `RunPolicy`.
- **Упрощённая реализация:** `RoleRunner` собирает сообщения; артефакты можно хранить в памяти или локальных файлах, без отдельной базы.
- **Расширение:** отдельный долговременный `ArtifactStore` для prompts, outputs, diff и test results с redaction.

### Бюджет (обязательное ядро) и model routing (расширение)

Для обязательного ядра зафиксируйте один provider/model и установите конечные лимиты вызовов, времени и повторов. Не допускайте тихого переключения на другой или платный endpoint.

**Расширение:** добавьте маршрутизацию по детерминированной политике и ограниченной классификации задачи:

| Тип шага | Начальный выбор | Условие эскалации |
|---|---|---|
| Извлечение полей, нормализация, классификация | Маленькая локальная модель или обычный Python-код | Формат не прошёл schema validation или низкая уверенность |
| Анализ кода, планирование, сложный review | Привычная более сильная coding-модель; локальная — только после собственного eval | Не хватает доказательств, повторяется ошибка, высокий риск |
| Высокорисковое изменение / неоднозначные требования | Human gate до вызова implementer | Не эскалировать автоматически без лимита/разрешения |
| Простые проверки и маршрутизация | Python-правила, тесты и allowlist | Не вызывать LLM там, где достаточно детерминированной проверки |

Для local-first пути платного API не требуется. Облачный fallback — необязателен и потенциально платный: он должен быть явно включён, иметь лимит и не получать приватный контекст без отдельного разрешения. Для локального сравнения фиксируйте модель/tag, quantization, `num_ctx`, wall-clock, число вызовов, память и ручные исправления. Если provider не отдаёт token usage, не придумывайте оценку токенов.

**Расширение:** сравните две модели/provider-а на одном наборе задач; router должен иметь явные лимиты и уметь вернуть `needs_input`/`blocked`, а не бесконечно переключать модели.

### Состояние задачи

```text
run_id
issue
acceptance_criteria[]
allowed_paths[]
plan
human_plan_approved
repo_evidence[]
test_plan[]
proposed_patch
commands_requested[]
commands_approved[]
test_results[]
review_findings[]
iteration_count
status: planning|needs_approval|implementing|testing|blocked|done
```

Секреты, `.env`, токены и содержимое credentials не должны попадать в промпты, артефакты логов или commit. Используйте `.gitignore`, redaction и отдельный учебный репозиторий.

## Практика

Соберите первую цепочку без автоматического shell:

```text
issue → planner → schema validation → человек утверждает план
     → read-only analyst → один отчёт
```

На выходе программа печатает артефакт и предлагает следующий шаг; она не меняет код. Добавьте тесты на invalid schema, provider timeout и `needs_input`.

**Что переносится за пределы coding agents?** Явные state, адаптер внешнего сервиса и конечные retry-бюджеты полезны в любом интеграционном workflow.

# Неделя 6. Tool calling, разрешения и policy

## Материал

Любой agent runtime может иметь доступ к чтению/редактированию файлов и запуску команд. Разделяйте:

- модель предлагает вызов инструмента;
- клиент интерпретирует вызов;
- политика разрешает или отклоняет его;
- пользователь подтверждает побочный эффект.

Не считать эти уровни взаимозаменяемыми. Хороший тест — дать модели инструкции вызвать только безопасный read-only инструмент и убедиться, что некорректный аргумент отклоняется до исполнения.

**Tool design — часть agent design.** Tool — интерфейс между моделью и внешней системой; неясное имя, широкая ответственность или шумный ответ затрудняют правильный выбор даже при хорошем prompt. Для каждого tool задайте:

- понятное имя и одну узкую ответственность;
- явные типизированные входы и краткое описание, когда его применять;
- предсказуемый, ограниченный по объёму результат с источниками;
- actionable errors: что не получилось и какой безопасный следующий шаг возможен;
- минимальные данные в результате и permissions, необходимые именно этому действию.

**Упражнение (7 минут):** перепроектируйте условный tool `repo_action(action, path, command, content, recursive)`, который читает и меняет любые файлы и запускает произвольную команду. Разделите обязанности на узкие интерфейсы чтения/поиска и запуска allowlisted теста; определите schema, ошибки и permissions. Объясните, почему новый интерфейс проще выбрать модели; по возможности сравните оба варианта на том же issue/eval с точки зрения корректности выбора и объёма результата.

**Расширение:** те же правила на реальной внешней системе. [Integration Lab](integration-lab.md) поднимает локальный REST-сервис issue поверх SQLite и проводит предложенный агентом вызов через цепочку `tools → permissions → policy → approval → execution → trace`: bearer-токен со scopes, allowlist репозиториев, проверка аргументов, таймаут, ограниченный retry только для чтения и human gate перед записью. API реализует удаление репозитория, но ни один инструмент агента его не оборачивает — это и есть least privilege на уровне registry, а не только на уровне prompt.

Если tool registry становится большим, не добавляйте все определения в каждый model call:

```text
registry с краткими метаданными
→ обнаружение подходящего tool по текущей задаче
→ загрузка описания и schema только найденных tools
→ вызов через обычную policy-проверку
```

Это dynamic tool discovery, а не разрешение модели создавать произвольные инструменты: поиск ограничен registry, а найденный tool всё равно проходит allowlist, проверку аргументов и разрешений. **Короткое упражнение:** для каталога из 30 tools выберите 3–5, нужных issue про pytest failure, и укажите, какие определения не следует загружать в этот вызов.

### Минимальная политика для курса

- читать только открытый учебный репозиторий и разрешённые подкаталоги;
- применять least privilege: выдавать каждой роли только необходимые права;
- проверять пути по allowlist и отклонять `..`, абсолютные и выходящие за корень пути;
- изменять только feature branch/worktree;
- не запускать shell-строки, составленные моделью, без просмотра человеком;
- хранить в конфиге allowlist точных тестовых команд; опасные команды (`rm`, `curl | sh`, `git push`, массовые миграции, публикация и деплой) не выполнять автоматически;
- не передавать модели secrets, `.env` и credentials; вывод инструментов и файлы проекта считать недоверенным контекстом, который может содержать prompt injection;
- перед изменением файла показывать diff;
- остановиться, если изменение выходит за scope утверждённого плана.

LLM не определяет собственные права: модель предлагает действие → runtime/policy проверяет инструмент, аргументы, путь и разрешение → только затем tool исполняется. Provider модели сам по себе не задаёт права агента. Для каждого IDE-инструмента (например, Kilo или Kodacode) настраивайте и проверяйте разрешения отдельно.

**Blast radius** — потенциальный масштаб последствий ошибочного или неверно разрешённого действия. Эвристика: `agent autonomy × access scope → potential blast radius` (это не количественная формула). Для каждого нового tool (shell, filesystem, Git, external API) спросите: что агент теперь может сделать, что произойдёт при ошибочном вызове, какие данные доступны, какие side effects возможны, нужен ли human approval и можно ли сузить permission? Связывайте ответ с least privilege и policy выше; human approval дополняет, но не заменяет техническое ограничение доступа.

## Обязательное ядро

На disposable-репозитории проверьте policy Python-workflow:

1. невалидный аргумент tool отклоняется до исполнения;
2. чтение и запись ограничены допустимыми путями;
3. запись и запуск команды требуют утверждения;
4. любое нарушение scope переводит запуск в `blocked`/`needs_approval`.

**Расширение:** повторить ручные сценарии в Kilo и/или Kodacode, сравнив их режимы разрешений с policy собственного orchestrator-а. Второй вариант — прогнать внешний API из [Integration Lab](integration-lab.md) и проверить, что право без approval, approval без права и отсутствие инструмента дают три разных отказа.

**Что переносится за пределы coding agents?** Policy и least privilege — общие принципы авторизации: любой внешний инструмент получает только необходимый scope, а недоверенные данные не могут расширить его права.

# Неделя 7. Оценка качества, трассировка и регрессии

## Материал

Оценивать надо весь pipeline, а не только итоговый ответ. Для обязательного ядра достаточно 5–10 issue из стартового набора: фиксируйте ожидаемое поведение, версии промптов/provider-а, структурированные выходы, решения человека и тестовые результаты. Не используйте приватные репозитории как публичные eval-данные.

Trace позволяет восстановить **почему** workflow пришёл к результату: какие узлы исполнялись, какие данные они получили, как выбрали tool, что инструмент вернул и почему система пошла по следующей ветке. Это не то же самое, что сохранять полный скрытый chain-of-thought; логируйте события и проверяемые артефакты, а не требуйте внутренние рассуждения модели.

### Минимальная схема trace-события

```json
{
  "run_id": "uuid",
  "parent_run_id": null,
  "node_id": "repo_analyst",
  "attempt": 1,
  "model_id": "provider/model-or-local-tag",
  "prompt_version": "repo-analyst-v3",
  "input_artifact_refs": ["artifacts/run/issue.json"],
  "tool_name": null,
  "tool_arguments_redacted": null,
  "output_artifact_ref": "artifacts/run/repo-evidence.json",
  "status": "complete",
  "duration_ms": 1200,
  "error_type": null,
  "transition_reason": "evidence_schema_valid"
}
```

Сохраняйте tool result, exit code и trace spans отдельно от промпта, связывая их через `run_id`/`node_id`. Перед логированием удаляйте ключи, токены, персональные и иные чувствительные данные; задайте срок хранения. Не логируйте без разбора весь репозиторий, скрытые рассуждения модели или полный environment.

### Метрики

- issue resolution rate — выполнены ли критерии приёмки;
- regression rate — внесены ли новые ошибки;
- test pass rate — прошли ли определённые до изменения тесты;
- reviewer precision — доля полезных замечаний без ложных срабатываний;
- scope adherence — менялись ли только разрешённые пути;
- tool-call success — валидны ли аргументы и вызван ли правильный инструмент;
- human intervention — число вмешательств и минуты проверки;
- latency / tokens / memory — длительность и нагрузка локального прогона;
- cost — измеренная стоимость вызовов, если provider её сообщает.

Не сводите эти метрики в один «магический» score. Evaluation нужна не только для проверки готового агента, но и для архитектурного выбора: сравните single-agent baseline и multi-agent workflow на одинаковых issue, критериях, лимитах и среде. Дополнительный agent, handoff, tool или model call увеличивает latency, токены/стоимость, сложность и поверхность отказов; сохраняйте его только при измеримой пользе. LLM-as-judge можно использовать как дополнительный сигнал, но не как замену тестам и человеческому code review.

**Короткое упражнение (10 минут):** посчитайте те же метрики для retrieval на наборе из [RAG-лабораторной](rag-lab.md): какая доля поддерживаемых вопросов нашла ожидаемый документ, какая доля ответов целиком опирается на процитированный фрагмент и появились ли ответы без источника. Измеримый показатель полезнее объяснения, почему retrieval «выглядит работающим»: неподкреплённый ответ и релевантный, но неиспользованный контекст — разные отказы с разными исправлениями.

### Набор тестов на отказ

Для каждого отказа фиксируйте цепочку `failure → detection → recovery/escalation → final state`. Retry допускается только в заданном лимите; перед повтором tool с побочным эффектом проверяйте, не выполнился ли он уже.

| Failure | Detection | Recovery / escalation | Final state |
|---|---|---|---|
| Missing information / ambiguous request | Planner находит неизвестный критерий или конфликт требований | Задать конкретные вопросы; не запускать implementer | `needs_input` |
| Invalid structured output | Schema validation завершилась ошибкой | Один ограниченный повтор с ошибкой валидации; затем остановить pipeline | `blocked` |
| Tool failure / timeout | Явное исключение, timeout или отсутствующий результат/exit code | Ограниченный retry только для безопасной идемпотентной операции; иначе сообщить человеку | `blocked` |
| Policy violation / dangerous command | Policy отклоняет инструмент или аргументы до исполнения | Не исполнять; записать причину в trace и запросить review при необходимости | `blocked` |
| Scope violation | Сравнение предложенных путей с утверждённым scope | Отклонить изменение; запросить подтверждение расширения scope | `needs_approval` |
| Baseline/test failure | Runner сохраняет команду, exit code и вывод | Различить известный baseline failure и новую регрессию; при новой ошибке вернуть implementer-у ограниченную доработку | `done`, если проверки прошли; иначе `blocked` по лимиту |
| Reviewer loop | Повторные замечания/неизменившийся diff или исчерпан лимит итераций | Прекратить цикл, передать diff и нерешённые замечания человеку | `needs_approval` |
| Prompt injection в issue/tool output | Контент помечен как недоверенные данные; политика проверяет действие независимо от текста | Игнорировать инструкции из данных; запрещённое действие не запускать, событие записать | `blocked` при попытке нарушения |

## Протокол сравнения и практика

Сравните одиночного агента и multi-agent workflow на одинаковом наборе, с одинаковыми критериями, бюджетом и тестовой средой. Для каждого прогона зафиксируйте:

- выполнены ли acceptance criteria и прошли ли тесты;
- регрессии, нарушения scope и запрещённые действия;
- время, число вызовов и минуты человеческой проверки;
- provider/model, версию промпта и настройки, необходимые для воспроизведения.

Не меняйте одновременно модель, промпт и архитектуру. Не требуется доказывать, что одна модель лучше другой; цель — выяснить, добавила ли оркестрация пользу в выбранном сценарии.

**Критерии приёмки эксперимента:** ни одного успешно выполненного запрещённого действия; каждый итог проверен тестом или человеком; отчёт явно показывает разницу в качестве/времени/вмешательствах. Универсального проходного score нет. Если multi-agent вариант не лучше baseline, зафиксируйте этот результат, а не усложняйте систему без причины.

Добавьте к ключевым шагам trace-событие. Разберите неудачный запуск по trace и артефактам: найдите первый неверный переход и отделите ошибку модели от ошибки схемы или инструмента. **Расширение:** сравните локальную и облачную/IDE-модель или измените один параметр за раз.

**Артефакт недели:** trace одного успешного и одного неуспешного запуска, приватные поля отредактированы; короткий root-cause отчёт и регрессионный тест на найденную причину.

**Что переносится за пределы coding agents?** Метрики, traces и отказные сценарии позволяют сравнивать архитектуры любого автоматизированного workflow по качеству, стоимости и вмешательству человека.

# Неделя 8. Capstone и разбор архитектуры

## Сначала business framing

Capstone начинается не с кода, а с короткого документа `problem-definition.md` в вашем репозитории. Он отвечает на вопрос, какую задачу вы автоматизируете и почему для неё нужен именно agent-подход. Шаблон:

```markdown
# Problem
Какую конкретную проблему решаем? Для кого и как сейчас выглядит успех?

# Current process
Как задача выполняется сегодня, какими инструментами и сколько это занимает?

# Pain point
Что именно плохо: дорого, долго, много ручной работы, много ошибок,
сложно масштабировать, постоянное переключение между системами?

# Proposed automation
Что именно автоматизируем, а что остаётся за человеком?

# Why an agent
Почему здесь нужен agent или workflow — или почему достаточно
детерминированной автоматизации: скрипта, cron, ETL, правила в CI?

# Architecture choice
Workflow или автономный агент? Один агент или несколько?
Какие tools, какой state, где нужны permissions, где human approval,
где нужен RAG, где достаточно обычного кода?

# Expected outcome
Чем измеряем результат: time saved, success rate, error rate,
доля ручных вмешательств, cost per task, latency?

# Risks
Неверное действие, выдуманный ответ, утечка данных, избыточные права,
нежелательные побочные эффекты, неконтролируемый расход.
```

Первый полезный вывод может быть отрицательным:

> **Здесь агент вообще не нужен.**

Если процесс детерминированный — разбор issue по правилам, отчёт по расписанию, проверка соответствия шаблону, — правильное решение написать обычный код с тестами и объяснить это в `problem-definition.md`. Это считается хорошим инженерным результатом, а не неудачей. Проверьте себя вопросом: **где в моей задаче нужна неоднозначность, которую нельзя заранее закодировать?** Если такого места нет, автономность только добавит стоимость, latency и новые точки отказа.

Обоснование архитектуры записывается в тот же документ, и техническое решение обязано на него ссылаться:

```text
Business problem
      ↓
Process analysis
      ↓
Automation opportunity
      ↓
Agent / workflow / deterministic automation
      ↓
Architecture
      ↓
Tools + permissions + state
      ↓
Implementation
      ↓
Evaluation
      ↓
Business outcome
```

Заполненный `problem-definition.md` — часть артефактов сдачи. К этому моменту из предыдущих недель у вас уже есть baseline, измерения и критерии; framing просто связывает их с задачей, которую вы решаете, и позволяет сразу отказаться от агента там, где он лишний.

## Реализуйте

Минимальный Python-workflow с topology:

```text
planner
  └─ человеческое утверждение плана
       └─ read-only analyst (код + тесты)
             ↓
       implementer (предлагает diff)
             ↓
       human approval before writes
             ↓
       test runner (только allowlisted команды)
             ↓
       reviewer (read-only, с доказательствами)
             ↓
       final summary + открытый PR/diff для человека, без автопубликации
```

## Обязательные элементы

- заполненный `problem-definition.md`, на который ссылается техническое решение;
- один provider за интерфейсом `ModelClient` и конфигурация его модели;
- явные схемы handoff/state и конечные лимиты повторов;
- read-only analyst и ограниченный implementer;
- allowlist путей/команд, human approval до записи/исполнения;
- обработка invalid schema, provider error и timeout без success-shaped fallback;
- тесты happy path и хотя бы трёх отказов, trace успешного и неуспешного запуска;
- README с запуском и известными ограничениями.

**Расширение:** отдельные specialist-роли, маршрутизация моделей, LangGraph, 10+ golden cases, checkpoint/resume и больше сценариев отказа.

## Критерии завершения основного курса

- `problem-definition.md` отвечает, почему выбран agent-подход, а не детерминированная автоматизация;
- минимум 5 сценариев из учебного набора;
- по каждому запуску можно объяснить, почему сработал именно этот агент/переход;
- недостающий факт или неопределённость приводят к `needs_input`, не к выдуманному ответу;
- ни один shell command/file write не исполняется без соответствующей политики и подтверждения;
- цикл ревью конечен;
- отчёт сравнивает baseline и workflow по качеству, времени и доле ручной работы;
- запуск воспроизводим в чистом учебном окружении.

## Архитектурный review

В финале ответьте:

1. Какие разделения на роли дали измеримую пользу, а где оказалось достаточно одного агента?
2. Какой узел самый дорогой/медленный?
3. Какие два узла можно безопасно параллелить и на каких данных?
4. Какие общие ошибки все роли могут унаследовать?
5. Где существует риск утечки данных или чрезмерных разрешений?
6. Что заменится при переходе с локальной модели на облачную, а что должно остаться неизменным?
7. Что не следует автоматизировать даже при улучшении модели?
8. Совпал ли измеренный business outcome с ожиданием из `problem-definition.md`, и что вы изменили бы в следующей итерации?

### Short-lived vs long-running agents

Короткий agent run обычно завершается в одном ограниченном цикле. У долгоживущего запуска контекст растёт, процесс может прерваться, а сохранённые предположения — устареть. Поэтому одного `while not done: call_model()` недостаточно: нужны persistent state и checkpoints, проверяемый resume после сбоя, контролируемые context compaction/reset, актуализация stale assumptions, bounded retries и явные stopping conditions. Связывайте это с human approval для значимых side effects, failure handling и trace, чтобы после восстановления было видно, что уже произошло и почему.

Подробная практика checkpoint/resume и idempotency — в неделе 12 [продвинутого трека](autonomous-agents.md); здесь достаточно объяснить, какие элементы нужны capstone, если его запуск выходит за один процесс.

## Что вы действительно освоили

После основного курса вы умеете:

- определить, нужен ли для задачи агент вообще;
- выбрать single-agent или multi-agent архитектуру и обосновать её baseline/eval;
- декомпозировать workflow на роли и проверяемые handoff-контракты;
- проектировать state/context и подключать tools через runtime;
- ограничивать permissions, применять allowlist и ставить human approval;
- задавать отказные переходы, bounded retry, escalation и конечное состояние;
- количественно оценивать задачу, регрессии, scope, стоимость и latency;
- анализировать traces и находить причину неверного перехода;
- отделять неизменную архитектуру от заменяемых моделей, providers и frameworks.

**Что переносится за пределы coding agents?** Capstone — частный случай управляемой автоматизации: те же контракты, policy, recovery и eval применяются к любому workflow с моделями и внешними инструментами.

## Расширения после capstone

Необязательно подключите LangGraph и перенесите в него тот же workflow. Сравните сложность state/checkpoint, наблюдаемость и удобство тестирования с простым Python-кодом. Не переписывайте проект на framework, если это не решает конкретную проблему.
